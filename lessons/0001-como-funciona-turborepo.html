Como funciona o Turborepo

Turborepo organiza tarefas já existentes em uma workspace e evita repetir trabalho. Ele não substitui o gerenciador de pacotes nem executa aplicativos por si só.

O modelo em uma imagem

package.json → descobre workspaces e scripts
turbo.json   → define ordem, entradas, saídas e cache
CLI          → monta o grafo e executa o necessário

apps/web → npm run build ─┐
apps/docs → npm run build ├─> Turborepo paraleliza e cacheia
packages/ui → npm run build ─┘

O Turborepo usa workspaces do npm, pnpm, Yarn ou Bun. Neste repositório, o gerenciador de pacotes declara apps/* e packages/* em [package.json](../package.json), enquanto turbo.json define os fluxos.

Este repositório em execução

npm run build roda turbo run build. Para a task build, ^build significa “construir primeiro as dependências de workspace”. As dependências @repo/ui são declaradas pelos aplicativos em seus próprios manifests.

{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "inputs": ["$TURBO_DEFAULT$", ".env*"],
      "outputs": [".next/**", "!.next/cache/**"]
    }
  }
}

dependsOn determina a ordem; inputs determina o que muda o hash; outputs diz ao cache quais arquivos restaurar. dev é persistente e não usa cache, pois é um processo longo.

Interpretação: trocar código em @repo/ui pode invalidar os builds que dependem dele. Trocar somente documentação pode não justificar executar tudo. Isso é decision making: Turborepo torna explícita a superfície afetada.

Deploy dos aplicativos

  1. Trate web e docs como projetos de plataforma independentes.
  2. Configure a Root Directory de cada projeto como apps/web ou apps/docs.
  3. Use o build do monorepo, por exemplo turbo run build --filter=web..., quando a plataforma precisar de dependências internas.
  4. Declare variáveis que afetam o build e configure a mesma variável na plataforma.

Deploy não é publicado em npm. Neste exemplo, os aplicativos podem continuar privados e os pacotes internos podem ser usados apenas dentro da workspace.

Monorepo ou repositórios separados?

Comece com monorepo quando equipes precisam fazer mudanças transversais com frequência e conseguem padronizar CI, tooling, releases e ownership. Comece separado quando os produtos têm ciclos, equipes, frameworks e requisitos de acesso muito distintos; custo de coordenação pode superar benefício de compartilhamento.

TurborepoNxWorkspaces sem build runner
Leve, aproveita scripts existentes, cache e filtrosMais plugins, boundaries e CI distribuídaMínimo investimento, menos automação

Para mais governança, Nx tende a ser mais opinativo. Para um monorepo JavaScript pequeno e scripts já estáveis, Turborepo é uma opção de baixo atrito.
